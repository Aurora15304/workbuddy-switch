# ADR-0001 跨账号迁移中的「不可迁移值」判定

- 状态：Accepted（2026-11-04）· 判定原则权威
- 作者：顾明析、叶探真
- 日期：2026-11-04
- 适用范围：连接器（MCP）配置与授权同步、会话跨账号同步
- 配套文档：`0002-cross-account-migration-invariant.md`（应用层逐资产矩阵与取证脚本）。**两文冲突时以本文为准。**
- 行号基准：本文所有 `File:Line` 对应 commit `031d245`；实现变更后行号会漂移，以符号名（函数名 / 字段名）为准定位。

## 背景

两项新功能都涉及「把 A 账号的数据搬到 B 账号」：

1. **连接器同步**：把某账号的 connector 配置与授权状态同步给其他账号。凭据落在
   `~/.workbuddy/connectors/{userId}/`（`connector-states.json`、`connector-states.v3.json`、
   `.credentials.v3.json`、`.master.key`）。
2. **会话跨账号同步**：把 A 账号的会话以新 id 复制给 B 账号。涉及
   `projects/{ws}/{cid}.jsonl`、`workbuddy.db:sessions`、sidecar 目录等。

**截至 2026-11-04，基于约 14 次 GitHub 仓库检索、约 20 个仓库元数据核查、8 个文档 / 页面
精读，这两项功能均未发现可复用的成熟范式**（样本量与逐条对标见 `docs/connector-sync-feasibility.md` §4）。
判定规则必须自建并留档，否则每一个新的可迁移字段都会重新辩论一次。

> **复现性等级：`方法可复现 / 结果不可复现`**（具体检索式未逐条留档；见可行性文档 §8.3）。
> 引用本条时**不得省略该等级标注**——与分类表强度标注同一元规则：**随文迁移，摘除即作废**，
> 不得沿用被摘标注后的版本。也不得读成「已可完整复核」。

> 口径说明：这是**负存在断言**（域 = 开源生态，无界且随时间变化），因此只能是**暂定**。
> 若发现任一实现：删除该判断并把方案改为「参考该实现」，不要保留「无先例」再补一句「除外」。

## 决策

### 一、判据（只有一条）

> **该值是否会被某个「裁决方」用来判定「你是谁」或「你此刻持有哪份凭据」。**
>
> - 有裁决方 → 不可迁移
> - 未发现裁决方 → 可迁移（可能需要改写主体标识字段，如 `id` / `user_id`）
>   ⚠️ 「未发现」是负存在断言：**必须先缩域到可穷举的范围再写**（做法见 §四 注 1），
>   直接写「无裁决方」即为违约。
> - 裁决方形态：**显式**（服务端 / 对端 / 网关 / 扩展）或**密码学**（AEAD authentication tag）

**注意：HKDF 等派生函数不是裁决方。** 它只做变换，不做 accept/reject；裁决发生在
AEAD tag 校验。混淆这两者会导致实现被写成「只重算 key」，而密文另有 AAD 绑定，
结果是所有字段 `InvalidTag`。

### 二、两条约束（不是判据）

约束**不对应任何判定分支，因此不得单独用于裁决任何值**，只能约束实现方式。

**约束 1｜生命周期副作用 → 禁写清单。**
某些对象的不可迁移性来自副作用而非裁决，不得写成判据的推论：

> `CredentialMasterKeyStore`：ACL 校验不可恢复地失败（或修复后仍失败）→ `tryReadKey`
> 返回 `undefined` → `getExistingAsync` 认定 primary / backup 皆无 → `getOrCreateOnce`
> 以 `randomBytes` 生成新随机 key → 原子覆写 primary + backup
> → 目标账号全部连接器密文永久不可解，且备份同被覆盖，无回滚路径。
>
> 方法名出自**客户端 `app.asar`**（`main/auth-liveness.js`，类 `CredentialMasterKeyStore`），
> 不在本仓 `crates/` 内——在本仓 `grep` 这些方法名会零命中（实测 `tryGetOrCreate` 0 次、
> `tryReadKey` 0 次），属预期，不代表约束不成立。
> **`tryGetOrCreate` 是不存在的方法名**（本仓与客户端源码均零命中），不得再引用。
>
> **但「读」要分三种，只有一种算写**——一刀切会误删唯一可靠的取证手段：
>
> | 读法 | 举例 | 进客户端逻辑 | 算写 |
> | --- | --- | --- | --- |
> | OS 层读 | `sha256sum` / `ls` / `python` 读 JSON | 否 | **不算**，真只读 |
> | **复刻客户端读逻辑** | 把 `getExisting*` 抄进本仓 Rust 代码 | **是** | **算写** ← 最易漏 |
> | 客户端 API 读 | 经客户端进程 / IPC 调 `tryReadKey` | 是 | **算写** |
>
> 第二行才是本条的陷阱：实施者读源码后把 `getExisting*` 复刻进来「只是判断密钥在不在」，
> 而该函数在「primary 有 / backup 无」时**补写 backup**（`recovered-backup-from-primary`）、
> 两侧不一致时**用 primary 覆盖 backup**（`mismatch-primary-wins`）——读的过程中把备份改掉。
>
> 所以禁写条款的精确形态是：**禁写 `.master.key` 与备份，并禁止任何复刻或调用客户端凭证栈
> 读逻辑的「存在性探测」；OS 层只读不在禁列**（`sha256sum` 复核三账号密钥互不相同是对的用法）。
> 实施建议里**不得出现**「先用客户端 API 探一下密钥在不在」——那一步在源码层面看不出是写。
>
> 现状补充：本仓 `crates/` 对 `master.key` 命中 **0 次**。今天是**纯设计期**约束，尚无既有
> 代码路径——所以它约束的是未来实现者的动作，不是现有缺陷。

禁写清单：

- `~/.workbuddy/connectors/{userId}/.master.key`
- `~/.workbuddy-key-fallback/connector-keys/{sha256(userId)[:32]}.key`

**约束 2｜覆盖率与可迁移性正交。**
覆盖率证据只能出现在「必要性」列（证明缺失不坏），**禁止出现在「裁决」列**
（证明能不能搬）。频率与可迁移性无关：`.credentials.v3.json` 覆盖率高但绝不可搬；
只出现过一次的会话正文覆盖率低但该搬。

### 三、推论：highest-restriction-wins

容器不可分拆时（单文件即一次原子落盘单位），按容器内**最严字段**裁决整个容器。

例：`.meta.json` 内含 `cwd`（可迁移）与 `acpConnectionId`（不可迁移）→ 整文件不搬。
理由不是 `cwd` 不可迁移，而是**文件不能拆半个**。

### 四、分类表

| 对象 | 归类 | 裁决方 | 强度 |
| --- | --- | --- | --- |

| `edge_sync_mapping.msg_channel = convmsg:{uid}` | 不可迁移 | edge-sync 扩展（云端归属） | `[代码·拒绝未观测]` |

| `.master.key` | 禁写（约束 1） | 非判据推论 | `[代码]`·不可实测（红线） |

> **锚点分区**：第 6、8 行的 `[实测]` 指**本机实测**，**不适用**文件头的 `commit 031d245` 代码快照锚点；其余各行的 `[代码]` / `[推断]` 才对应 `031d245`。混用会把全表仅有的 2 行实测降级成代码推断。
>
> 两行实测的复跑参数（缺任一项都复现不出结论）：
> - 第 6 行 · 合成向量双向反例：真实 `masterKey` + 真实 `salt` + 真实 `userId` 构造 cipher，同 salt 换 userId、同 userId 换 masterKey 均得 `InvalidTag`；**未用真实连接器密文**（三 profile 的 `connectors` 均为空）。
> - 第 8 行 · 零命中扫描：词表 `"userId"` / `"user_id"` / `"accountId"`（**必须带引号**，否则会命中正文里提到字段名的自然语言）；域 `~/.workbuddy/projects/**/*.jsonl`，**分母 963**（含 `subagents/`）；命令 `grep -rl --include="*.jsonl" '<词>' ~/.workbuddy/projects | wc -l` → 三者均 **0**。**`--include` 不可省**：省掉时本机实测返回 **1**，命中的是 sidecar 里 `tool-results/call_*.txt`（大输出渲染文件，含对话正文），不是 transcript——这也是注 1 第 2 条"平稳"要求选子域的现场样本。
>
> **锚点变更即全表重验**：commit 变更或重跑实测时，**受影响的行必须重新取证**，不得只改锚点文字。改一次 hash 就让 9 行结论自动"续期"，是本条要防的静默失效。

#### 注 1｜第 8 / 9 / 10 行的域收缩（原「无裁决方」不成立）

原写法「无裁决方」若指「**所有可能的消费方**」，则是负存在断言且域无界（未来客户端版本
可能新增校验），不可判定。但决策需要的域**不是那个**，而是「**本版本客户端的全部消费方**」
——后者**有界、可穷举**。

收缩必须**分半写**，只写本机侧即为不成立的收缩：

> **本机侧（已穷举）**：在本版本客户端（commit `031d245`）中**未发现裁决方**。
> 穷举范围：`crates/` 全部模块对目标文件的消费点 + 客户端 `app.asar` 对目标文件的全部
> 消费点（`rebuildSessionIndexFromHistory`、`applyGatewayHeaders`、`VlmSessionLedger` 等）。
>
> **服务端侧（未观测）**：会话正文经 edge-sync 上传，云端按 `uid` 归属（见 §四 第 5 行
> `msg_channel = convmsg:{uid}`，以及「禁写 `edge-sync-mapping`」一条——预写会让扩展判定
> 已迁移而跳过上传，云端缺会话）。**该侧是否拒绝跨账号正文，本机无法观测。**
>
> **单触发器：若任一侧发现裁决方，该行改为不可迁移。**

只写本机侧比原写法更危险：它把「**服务端不裁决**」这个同样未验证的结论偷偷塞进断言里，
只是把错误缩小到看不出来。原写法错得显眼，半截写法错得隐蔽。

为什么合成**一个**触发器、而不是两侧各写一句：分开写的话，将来只推翻一侧时，另一侧会
继续留在原地充当依据——那时没人会想到要去改它。**一条判断只应有一个作废条件。**

**缩域前必须先做一次反向查询：本文档是否已经承认存在一个不在该域内的裁决方？**
若有，缩域不成立。

本表就命中了这条：§四 第 5 行自认 `convmsg:{uid}` 的裁决方是 edge-sync 扩展、云端在问
「这会话归谁」，而可穷举的域只有本机 `crates/` + `app.asar`。**规则违反了自己文档里已有
的分类**——这比外部反例更狠：不需要任何新证据，回头读一遍自己的表就能发现。

**取证口径：负存在断言的域必须同时满足三条，缺一不可。**

1. **有界**——`crates/` 有界；「所有可能的消费方」无界 → 缩域。
2. **平稳**——域内的东西不能在我们取证的同时被改动。
   `~/.workbuddy/projects/**` **不平稳**：同一命令连跑三次，命中集 `2 → 1 → 1`，其中一个
   `subagents/<agent>/tool-results/*.txt` 在两次取证之间被删除；而会话运行与**排查自身**
   都往这个目录里写（我们自己就是写入源之一）。
   `~/.workbuddy/projects/**/*.jsonl` **平稳**（三次均 0）——选稳定子域，不选大目录。
3. **可重跑**——命令必须与断言的数量词同域：说「正文」就只能查 `--include='*.jsonl'`。

**第 2 条不能靠「更谨慎」解决**——它要求换观测对象，不是换措辞。实证：不加过滤递归搜
`"accountId"` 命中 1–2 个文件，全部是 `tool-results/*.txt` 里捕获的**代码片段**
（`json!({"accountId": "a", "email": "same", "result": "already"})`），不是正文；
正文域三次恒为 0。**「零命中」若建立在活域上，会被下一次排查自己写坏。**

本表的「本机侧已穷举」指 `crates/` 与 `app.asar` 的**快照**，不指运行中的数据目录。

方法论（本条比三行修正更耐用）：
> **域无界时的第一反应是缩域，不是降级；只有缩不动时才降级。**
> 「暂定」把判断成本推给读者（谁都不知道能不能用）；「缩域」把它前置给写作者，并给出
> **可执行的穷举动作**。

#### 注 2｜证据强度（强度已作为表内一列，请勿与裁决列混读）

强度**是表的一列，不是表外的说明**——写成列，就无法只摘走「不可迁移」而留下「这是推断」。
这也是注 3 唯一可结构化的实现方式。

- **`[实测]` — 2 行**
  - 第 6 行 `连接器密文`：用真实 `master.key` + 真实 `salt` + 真实 `userId` 构造 cipher，
    同 salt 换 userId、同 userId 换 masterKey 均得 `InvalidTag`。**是合成向量**，
    未用真实连接器密文验证（本机 3 个 profile 的 `connectors` 均为空）。
  - 第 8 行 `会话正文`：**负断言**。域 = `~/.workbuddy/projects/**/*.jsonl`（**含
    `subagents/`**，分母 **963**），对 `"userId"` / `"user_id"` / `"accountId"` 三词零命中。
    **分母必须写死**：换全库口径 `~/.workbuddy/**/*.jsonl` 是另一个数（2026-11-04 12:1x 实测 **4823**，
    且该数随会话被清理而**单调下降**——同日三读为 4852 → 4823 → 4792，是趋势不是抖动，
    故**不得作为常量引用**）。「正文可搬」只在「963 这个域」内成立，跨域即失效。
- **`[代码·拒绝未观测]` — 2 行（第 4、5 行）**：机制是代码事实，但**拒绝行为从未观测**。
  写成 `[代码]` 会被读成「已验证会拒绝」。第 4 行依据：`buildAcpHeaders()` /
  `applyGatewayHeaders` 把 `acp-connection-id`、`acp-session-token` 与 Bearer 一并作为
  请求头发出——**是三件套，不是单个头名**（单说某一个头都会漏）；但未观测过网关拒绝过期租约。
- **`[代码]` — 3 行（第 9、10、11 行）**：如 `sessions` 读写按 `WHERE user_id = ?` 过滤；
  第 11 行的禁写来自约束 1 的生命周期副作用，**不可实测（属红线，测一次就毁掉目标数据）**。
- **`[推断]` — 4 行（第 1、2、3、7 行）**：拒绝行为全部未观测。第 7 行的不可迁移性
  **继承自第 4 行**——第 4 行一旦被推翻，第 7 行一并不成立，不得单独保留。

- **`file:line` 类引用必须同处标 `commit:<hash>`**：代码一改，行号就漂——本轮实例是
  `session_sidecar.rs` 的「白名单 `:63-66`」已漂到 `:62-65`，原因恰是**建议被采纳**
  （`SIDECAR_SUBDIRS` 改成了表驱动）。无 hash 的 `file:line` 视为**弱证据**，不得单独
  支撑「不可迁移」这类裁决。理由：它的失效条件天然存在（代码会改），却没有到期检测手段，
  不标 hash 就必然静默腐烂；标了 hash，漂移可被一次 `git diff` 检出——
  **把不可检测的腐烂变成可检测的漂移。**（本文行号基准统一为 commit `031d245`，见文首。）

**推论**：11 行里只有 2 行是实测，**其余 9 行不是**。判据逻辑上可判定，但支撑证据以代码
推断为主；实施前若把本表当验收依据，应逐行补一次外部行为观测，在那之前它是「读代码得出的
预测」，不是「观测到的行为」。

#### 注 3｜引用约束

> 引用本分类表时，强度标注必须**随表整体迁移**，不得摘除、不得单独改写某行。
> 若摘除或改写：**该引用视为作废，须回退到原文核对**，不得沿用被摘标注后的版本。

理由：源文档写得再严也没用——**摘标注发生在下游，不在源头**。每经过一次引用就衰减一次，
所以约束必须随表走。

#### 注 4｜状态锚点（注 2、注 3 的上位规则）

> **凡引用状态——行数、md5、`file:line`、star 数、命中数——必须同处写时点或 commit。
> 不带锚点的状态引用一律视为传闻，不得作为依据。**

本轮每一次「事实冲突」都是这条被违反，而各种错法只是同一个动作的变体：
**用一个便宜的代理指标代替核对。**

| 变体 | 代理指标 | 本轮实例 |
| --- | --- | --- |
| 措辞像 | 词形代替逻辑形式 | 「四方向零同构」被当成不含否定词、因而不再需要穷举 |
| 结构像 | 并列清单代替消费方行为 | 兄弟文件与正文同列，被当成同等待遇 |
| 口气像 | 他人转述代替一手检索 | 引「你其实已经有写授权」——话存在，但收件人不是我 |
| 时点像 | 某次快照代替当前状态 | 「0001 = 229 行」；「白名单 `:63-66`」 |

所以不必背四种，只记一条：**引用状态，就带锚点。**

附带一条自证：本文写作过程中，我自己量到的行数与 md5 也曾是**撕裂读**——写完立刻
`wc -l`，编辑工具还在 flush，读到的比真值少两行。**连写者本人都不能信自己刚写完的那次
读数**，所以这条必须是硬规则，而不是自觉。

## 具体裁决

1. `.master.key` 与 `key-fallback` 备份 key **一律不复制、不搬运、不「临时借用」**。
2. OAuth token **不搬运**。改为目标账号侧重新走 OAuth 授权。可同步的只有无身份语义的
   配置：server URL、`headerOverrides` / `envOverrides` 的**键名**、`enabled` 开关。
3. `.meta.json` / `.file-rollback.ndjson` **显式不搬**。需落 Non-Goal 一条 + 回归断言：
   目标会话目录下不得出现源侧这两个文件。
4. 会话正文 `.jsonl` 迁移 + sidecar 按新 cid 重建；DB 写入必须 `verify_session_row`
   回查（防 `INSERT OR IGNORE` 静默 0 行）。

## 方法论：静默是这套体系的默认姿态

三个失败点分属三层，**没有一个会把错误抛到用户眼前**：

| 层 | 静默失败形态 | 被什么吞掉 |
| --- | --- | --- |
| 密码学 | `InvalidTag` | `decryptValue` 的 catch → 按「未授权」处理 |
| 文件可选性 | 元信息缺失 | `d = {}` 降级，字段回落 jsonl / `stat` |
| 身份核对 | token 被删 | `clearManagedAuthHeaders()`，功能「看起来没生效」 |

由此得出：

1. 自验标准不是质量要求，而是**把静默失败强制转为可观测失败的唯一手段**；
2. 三层失败成因不同，「加一行日志」这类单一修法不可能覆盖，必须**逐层自验**；
3. **「用户说没生效」不能作为结论，也不能当噪音丢弃。**
   用户是**触发器，不是定位器**：他推翻的是「功能可用」，推不出「哪一层坏了」。
4. **日志属系统层，用户报告属结果层，两者作用域不相交。** 用系统层证据反驳结果层
   断言是**层级错配**，不是证据不足——换哪份日志都没用。正确动作是触发起分层自验。

## 方法论：并列清单与其配对

> **为什么容易错**：并列清单只说明「同属一类」，不说明「同等待遇」；
> 待遇必须由消费方行为决定。
> **怎么发现错**：不要「再想一遍」，要**再往下读一层代码**或**往下追一个反例**。

依据：本轮三次修正（兄弟文件搬不搬、判据维度、`tool-results` 分层）**没有一次是推理链
自我否定的产物**，全部来自「往下再读一层」或「往下追一个反例」。

## 方法论：规则的第一次应用对象，应该是承载它的那份文档

> 规则写完后，**先用它审一遍自己所在的这份文本**，再拿去审别人。

依据：本文三次违反自己写下的规则，原因都不是不严谨，而是**写完没回头用**——
写规则时是立法者视角，写完立刻切回作者视角，规则就不再作用于自己的产物。

同类症状还有两处可辨认：

## 其他必须留档的约束

- **禁写 `edge-sync-mapping-v{N}.db`**：预写会让 edge-sync 扩展判定「已迁移」而跳过上传，
  云端缺会话，后续 RENAME / ACTIVITY 404。
- **`edge_sync_mapping` 只读探测**存在性与版本，不写一个字节。
- **`updated_at` 是 ms 整数**，可作 `(updated_at, id)` keyset 增量游标；**软删必须当状态
  传播而不是跳过**（实测 663 行中 35 行 `deleted_at IS NOT NULL`，是活路径）。
- **双数据根**：CN 走 `~/.workbuddy`，AI 走 `~/.workbuddy-ai`。跨档取锁顺序固定
  `Cn → Ai`，**任何路径不得反序**（否则死锁）。
- **枚举 profile 的判据**是「目录内有 `.master.key` 且 `connector-states.json` 有 v4 header」，
  不是「目录名像 UUID」。`default` 目录会被客户端 `assertUserId()` 显式拒绝
  （`refuse to operate with userId='default'`）。

## 附录 A · 实施前置约束（**不构成实施批准**）

本 ADR 对连接器授权同步的结论是**不做搬运**（见 `docs/connector-sync-feasibility.md`）。
本节记录的不是实施指引，而是「若未来决定实施，则不可省略的约束」，目的是防止无此约束的实施。
**任何读者不得将本节理解为已批准方案。**

1. **key 与 AAD 必须同时重算**
   - `key = HKDF-SHA256(ikm = masterKey ‖ userId, salt = header.salt, info = "workbuddy-oauth-credentials-v1", 32B)`
   - `AAD = "${userId}|${serverKey}|${fieldName}"`
   - **只换 key 不换 AAD → 依然 `InvalidTag`。**
2. **`serverKey` 命名空间按落点不同，须逐文件逐字段**
   - `connector-states:headerOverrides:<id>`
   - `connector-states:envOverrides:<id>`
   - `McpCredentialStore` 的 slot key（`${serverName}|${sha256(JSON({type,url,Headers})).slice(0,16)}`）
   - **禁止「重算一次 key 全库通用」。**
3. **三个写入点必须齐全，且视为同一事务的产物**
   - `connector-states.json`(v4)
   - `connector-states.v3.json`（降级镜像，**必须与 v4 共用同一份 header**）
   - `.credentials.v3.json`（OAuth token 的真正落点，最容易被漏）
   - 任何中途中断**不得留下**「v4 已换新 header、v3 仍为旧 header」的中间态。该缺陷当时
     不报错（`readStates` 只读 v4 优先），但一旦降级 / 回滚就会读到旧 header。
4. **必须把 `accountIdentityKey` 改写为目标身份**
   否则客户端启动时 `ensurePersistentStateMatchesCurrentIdentity()` 会调
   `clearManagedAuthHeaders()` **静默删掉受管 `Authorization` / `X-Oneid-Access-Token`**
   —— 症状是「同步完了但没生效」，用户看不到任何报错。
5. **必须客户端完全退出**
   客户端无任何文件监听（`watch(` / `chokidar` 命中数为 0），内存态会在下次
   `savePersistentState()` 整体回写，覆盖外部改动。
6. **禁写**：`.master.key` 与 `~/.workbuddy-key-fallback/connector-keys/*.key`（约束 1）。
7. **分层自验标准（缺此则不可交付）**
   - 密码学层：用**目标** `userId + masterKey + header` 构造的 cipher 必须能成功解密
     **每一个**字段，且 `verifyHeader(targetUserId, targetMasterKey)` 返回 `ok`
   - 文件层：三个写入点必须同时存在且 header 一致
   - 身份层：`accountIdentityKey` 等于目标身份
   - 任一失败即视为不可交付，**不得以「部分字段成功」报告完成**

## 残余风险（不得在方案卡中写成已确认）

- 真实 connector 条目 schema 未观测（本机 3 个 profile 的 `connectors` 均为空）。
- `accountIdentityKey` 仅观测到 `||enterprise` 后缀，`||personal` 变体未知。
